# AutoSpec Benchmark Harness

Cross-model benchmark for the AutoSpec QUICKSTART pipeline. Runs identical prompts
through Claude and GPT, scores outputs against 28 quality gates, and compares results.

---

## Prerequisites

| Requirement | Version | Install |
|-------------|---------|---------|
| **Claude Code CLI** | latest | `npm install -g @anthropic-ai/claude-code` |
| **OpenCode CLI** | v1.2.26+ | See [opencode.ai](https://opencode.ai) |
| **jq** | 1.6+ | `apt install jq` / `brew install jq` |
| **python3** | 3.8+ | `apt install python3` / `brew install python3` |
| **bash** | 4.0+ | Pre-installed on Linux; `brew install bash` on macOS |

**API Keys** (set in environment before running):

```bash
export ANTHROPIC_API_KEY="sk-ant-..."
export OPENAI_API_KEY="sk-..."
```

## Quick Start

### Full Benchmark Run (Claude + GPT, 3 runs each)

```bash
cd /opt/FitnessAiManager/autospec/benchmark
./harness.sh run-all
```

### Dry Run (no API calls — validates pipeline locally)

```bash
DRY_RUN=true ./harness.sh run-all
```

### Score Only (no model invocation)

```bash
./scorer.sh examples/taskflow/
```

### Compare Two Results

```bash
./compare.sh results/run-20260315/claude/ results/run-20260315/gpt/
```

## Usage

### Harness (`harness.sh`)

```bash
./harness.sh run-all                               # Default: 3 runs, claude+gpt, taskflow target
./harness.sh run-all --runs 5                      # 5 runs per model
./harness.sh run-all --models "claude"             # Claude only
./harness.sh run-all --models "claude,gpt"         # Both models (default)
./harness.sh run-all --target ../examples/mealmap  # Different target project
./harness.sh run-all --output results/my-run       # Custom output directory
```

The harness creates a timestamped run directory:

```
results/run-20260315-143022/
├── claude/
│   ├── run-1/   run-2/   run-3/      ← individual runs
│   ├── aggregate-scores.json          ← mean ± stddev across runs
│   └── metadata.json
├── gpt/
│   ├── run-1/   run-2/   run-3/
│   ├── aggregate-scores.json
│   └── metadata.json
└── comparison.md                      ← generated by compare.sh
```

### Standalone Scorer (`scorer.sh`)

```bash
./scorer.sh /path/to/autospec/project/    # Score any project directory
./scorer.sh examples/mealmap/             # Score MealMap (viewer gates active)
./scorer.sh examples/taskflow/            # Score TaskFlow (viewer gates skipped)
```

Outputs `scores.json` in the project directory (or specified output path).

### Aggregate Scoring

```bash
./scorer.sh --aggregate results/run-20260315/claude/   # Mean/stddev across all run-N/ dirs
```

Outputs `aggregate-scores.json` with mean, stddev, min, max per category and overall.

### Comparison Engine (`compare.sh`)

```bash
# Compare two model result directories
./compare.sh results/run-20260315/claude/ results/run-20260315/gpt/

# Write comparison to a custom file
./compare.sh results/run-20260315/claude/ results/run-20260315/gpt/ --output my-comparison.md

# Works with single run dirs too (uses scores.json)
./compare.sh results/run-20260315/claude/run-1/ results/run-20260315/gpt/run-1/
```

Accepts either model-level directories (with `aggregate-scores.json`) or individual
run directories (with `scores.json`). Writes `comparison.md` to the parent of `<dir1>`
unless `--output` is specified.

## Quality Gates

28 gates across 6 categories evaluate each model's AutoSpec output:

| Category | Weight | Gates | Description |
|----------|--------|-------|-------------|
| `structure` | 20% | STR-01–STR-05 | Required files exist, correct directory layout |
| `specificity` | 25% | SPC-01–SPC-06 | Tech stack named, endpoints defined, schema specified |
| `sdd_compliance` | 20% | SDD-01–SDD-05 | Backlog format, sprint tickets, role specs present |
| `coherence` | 15% | COH-01–COH-04 | Cross-references valid, no contradictions, naming consistent |
| `viewer` | 10% | VWR-01–VWR-04 | Viewer app present and buildable (conditional on viewer/ dir) |
| `technical_correctness` | 10% | TC-01–TC-04 | Valid JSON/YAML, no broken shell scripts, schema parseable |

Full gate definitions: [`docs/benchmark/02_quality_gates.md`](../docs/benchmark/02_quality_gates.md)

### Score Interpretation

| Range | Rating | Description |
|-------|--------|-------------|
| 90–100 | **Excellent** | Comprehensive, specific, well cross-referenced |
| 75–89 | **Good** | Solid coverage, minor gaps |
| 60–74 | **Adequate** | Meets minimum structure, lacks depth |
| 40–59 | **Poor** | Significant structural gaps |
| <40 | **Failing** | Core outputs missing |

## Scoring Details

### Gate Check Types

| Type | How It Works |
|------|-------------|
| `file_exists` | Checks that listed paths are present in the output directory |
| `content_match` | Searches file content for required patterns (regex) |
| `json_valid` | Parses JSON with `jq`; fails on syntax error |
| `shell_valid` | Runs `bash -n` on each `.sh` file |
| `line_count` | Counts lines in a file; passes if above threshold |
| `cross_reference` | Checks that a value in file A appears in file B |

### Conditional Gates

Gates with `"conditional": true` are skipped if their prerequisite is absent:

- **Viewer gates** (VWR-01–VWR-04): skipped if no `viewer/` directory exists
- This prevents penalizing models when the benchmark target (TaskFlow) has no viewer

## Extensibility

### Adding a New Model

1. Create `lib/models/{name}.sh` with a single function:

   ```bash
   invoke_model() {
     local prompt_file="$1"
     local work_dir="$2"
     # Invoke your CLI here, writing output to $work_dir
     your-cli run --dir "$work_dir" < "$prompt_file"
   }
   ```

2. Add the model name to the `--models` flag:

   ```bash
   ./harness.sh run-all --models "claude,gpt,newmodel"
   ```

3. The `run_model()` dispatcher in `lib/common.sh` auto-sources `lib/models/{name}.sh`.

### Gemini (stub)

Create `lib/models/gemini.sh` when the Gemini CLI is available. The dispatcher already
supports arbitrary model names — no changes to `harness.sh` or `common.sh` required.

```bash
# Example gemini.sh stub
invoke_model() {
  local prompt_file="$1" work_dir="$2"
  gemini run --dir "$work_dir" --model "${GEMINI_MODEL:-gemini-2.0-flash}" < "$prompt_file"
}
```

### Adding a New Quality Gate

1. Edit `config/quality-gates.json` — add a gate object to the appropriate category array
2. Increment `total_gates`
3. Re-run `scorer.sh` to verify the new gate evaluates correctly
4. Update `docs/benchmark/02_quality_gates.md`

### Using a Different Target Project

```bash
./harness.sh run-all --target ../examples/mealmap
```

MealMap has a viewer app, so VWR gates will activate. TaskFlow does not.

## Known Confounding Variables

This benchmark measures **model + CLI + prompt** as a combined system, not the model alone:

1. **Model capability** — Core language model knowledge and instruction-following
2. **CLI file-access behavior** — Claude Code reads the filesystem natively; OpenCode uses `--dir` flag
3. **Context-window handling** — How each CLI chunks and presents the QUICKSTART prompt
4. **Prompt interpretation** — Sensitivity to phrasing, formatting, and section ordering
5. **Tool use** — Claude Code can call `bash`, `read`, `write` natively; OpenCode behavior differs

Sprint 24B aims to isolate these factors by running identical prompts via API (no CLI),
then comparing outputs directly.

## Model Version Pinning

For reproducible results, pin exact model versions:

```bash
CLAUDE_MODEL=claude-sonnet-4-20250514 GPT_MODEL=gpt-4o-2024-11-20 ./harness.sh run-all
```

Record the pinned versions in `results/run-DATE/metadata.json` for audit trails.
The harness writes `cli_version` to metadata automatically via `get_cli_version()`.

## Troubleshooting

### `jq: command not found`

```bash
sudo apt install jq        # Debian/Ubuntu
brew install jq            # macOS
```

### `No scores.json found`

Run `scorer.sh` first, or check that `harness.sh` completed without errors:

```bash
./scorer.sh results/run-DATE/claude/run-1/output/
```

### `python3: command not found`

```bash
sudo apt install python3   # Debian/Ubuntu
brew install python3       # macOS
```

### Dry run produces no diff

DRY_RUN mode writes mock output — `comparison.md` will show 0 scores. This is expected.
Use `DRY_RUN=true` only to validate pipeline structure, not scoring accuracy.

### OpenCode CLI not installed

```bash
# Check opencode docs at https://opencode.ai for current install instructions
opencode version
```
