# 04 — Database Architect Specification: TaskFlow

## Database Choice

| Property | Value | Rationale |
|----------|-------|-----------|
| **Engine** | SQLite | Single-user personal app; no concurrent multi-user writes. Zero-config, serverless, file-based — ideal for solo-developer budget and PWA offline model. Ships as a single file, simplifying backup and deployment. |
| **Version** | 3.45+ | WAL mode support, JSON functions, window functions, `STRICT` tables available. |
| **Driver** | `better-sqlite3` | Synchronous API avoids callback complexity in Express; ~5x faster than `sqlite3` async driver for single-user workloads. TypeScript types available via `@types/better-sqlite3`. |
| **ORM** | None (raw SQL via a thin repository layer) | SQLite-specific features (e.g., `WITHOUT ROWID`, FTS5) are easier to use without ORM abstraction. Aligns with `02_backend_lead.md` service-layer pattern where repositories execute raw queries. |

### WAL Mode

The database MUST be opened with `PRAGMA journal_mode=WAL;` to allow concurrent reads during writes (critical for dashboard queries while a sync operation writes). Additionally:

```sql
PRAGMA journal_mode = WAL;
PRAGMA busy_timeout = 5000;
PRAGMA synchronous = NORMAL;
PRAGMA foreign_keys = ON;
PRAGMA cache_size = -8000;  -- 8MB cache

## Schema Design

### Table: `users`

Single-user in v1, but the schema supports the auth contract from `02_backend_lead.md`.

| Column | Type | Nullable | Default | Constraints |
|--------|------|----------|---------|-------------|
| `id` | `TEXT` | NO | `(lower(hex(randomblob(16))))` | `PRIMARY KEY` |
| `email` | `TEXT` | NO | — | `UNIQUE`, `CHECK(email LIKE '%_@__%.__%')` |
| `password_hash` | `TEXT` | NO | — | — |
| `name` | `TEXT` | NO | — | `CHECK(length(name) >= 1 AND length(name) <= 100)` |
| `created_at` | `TEXT` | NO | `(strftime('%Y-%m-%dT%H:%M:%fZ','now'))` | — |
| `updated_at` | `TEXT` | NO | `(strftime('%Y-%m-%dT%H:%M:%fZ','now'))` | — |

- **Soft-delete: NO.** Single-user app — account deletion means full data wipe (hard delete cascade). No audit trail needed.
- `id` uses a hex UUID generated by SQLite's `randomblob(16)` — avoids external UUID dependency.
- Timestamps stored as ISO 8601 TEXT (SQLite has no native datetime type; TEXT is the recommended affinity for datetime comparisons).

### Table: `refresh_tokens`

Supports JWT refresh token rotation per `02_backend_lead.md` Auth Requirements.

| Column | Type | Nullable | Default | Constraints |
|--------|------|----------|---------|-------------|
| `id` | `TEXT` | NO | `(lower(hex(randomblob(16))))` | `PRIMARY KEY` |
| `user_id` | `TEXT` | NO | — | `REFERENCES users(id) ON DELETE CASCADE ON UPDATE CASCADE` |
| `token_hash` | `TEXT` | NO | — | `UNIQUE` |
| `expires_at` | `TEXT` | NO | — | — |
| `revoked_at` | `TEXT` | YES | `NULL` | — |
| `created_at` | `TEXT` | NO | `(strftime('%Y-%m-%dT%H:%M:%fZ','now'))` | — |

- **Soft-delete: YES** (via `revoked_at`). Revoked tokens are kept for rotation-detection (if a revoked token is reused, all tokens for the user should be invalidated — replay attack detection per `02_backend_lead.md`).
- Hard cleanup: a scheduled job (or on-login check) deletes tokens where `expires_at < datetime('now', '-7 days')`.

### Table: `categories`

User-defined task groupings per Product Manager spec AC-3.

| Column | Type | Nullable | Default | Constraints |
|--------|------|----------|---------|-------------|
| `id` | `TEXT` | NO | `(lower(hex(randomblob(16))))` | `PRIMARY KEY` |
| `user_id` | `TEXT` | NO | — | `REFERENCES users(id) ON DELETE CASCADE ON UPDATE CASCADE` |

- **Soft-delete: NO.** When a category is deleted, tasks referencing it have `category_id` set to `NULL` (see FK on `tasks`). This matches the PM spec: "deleting a category does not delete tasks."
- `UNIQUE(user_id, name)` — enforced via index (see Indexes section). A user cannot have duplicate category names.

### Table: `tasks`

Core entity. Aligns with Task model in `02_backend_lead.md`.

| Column | Type | Nullable | Default | Constraints |
|--------|------|----------|---------|-------------|
| `id` | `TEXT` | NO | `(lower(hex(randomblob(16))))` | `PRIMARY KEY` |
| `user_id` | `TEXT` | NO | — | `REFERENCES users(id) ON DELETE CASCADE ON UPDATE CASCADE` |
| `category_id` | `TEXT` | YES | `NULL` | `REFERENCES categories(id) ON DELETE SET NULL ON UPDATE CASCADE` |
| `title` | `TEXT` | NO | — | `CHECK(length(title) >= 1 AND length(title) <= 200)` |
| `description` | `TEXT` | YES | `NULL` | `CHECK(description IS NULL OR length(description) <= 2000)` |
| `priority` | `TEXT` | NO | `'medium'` | `CHECK(priority IN ('low', 'medium', 'high'))` |
| `status` | `TEXT` | NO | `'incomplete'` | `CHECK(status IN ('incomplete', 'complete'))` |
| `due_date` | `TEXT` | YES | `NULL` | `CHECK(due_date IS NULL OR due_date GLOB '[0-9][0-9][0-9][0-9]-[0-1][0-9]-[0-3][0-9]')` |
| `completed_at` | `TEXT` | YES | `NULL` | — |
| `created_at` | `TEXT` | NO | `(strftime('%Y-%m-%dT%H:%M:%fZ','now'))` | — |
| `updated_at` | `TEXT` | NO | `(strftime('%Y-%m-%dT%H:%M:%fZ','now'))` | — |

- **Soft-delete: NO.** Task deletion is a hard delete. The PM spec says "delete task" is a destructive action with a confirmation dialog — no need to recover deleted tasks. Completion stats count `completed_at IS NOT NULL` rows, so deleted tasks correctly disappear from stats.
- `due_date` is date-only (`YYYY-MM-DD`) — no time component, matching the frontend date picker behavior from `03_frontend_lead.md`.
- `completed_at` is set when `status` changes to `'complete'` and cleared when toggled back to `'incomplete'` — handled in the service layer.

### Virtual Table: `tasks_fts` (Full-Text Search)

SQLite FTS5 virtual table for full-text search on task title and description (AC-5).

```sql
CREATE VIRTUAL TABLE tasks_fts USING fts5(
  title,
  description,
  content='tasks',
  content_rowid='rowid',
  tokenize='unicode61 remove_diacritics 2'
);

- Synchronized via triggers (see Data Integrity section).
- `unicode61` tokenizer handles accented characters.
- Queries use `tasks_fts MATCH ?` with `bm25()` ranking.

## Migrations

### Strategy

Migrations are managed as numbered SQL files in `db/migrations/`:

db/
├── migrations/
│   ├── 001_initial_schema.sql
│   ├── 002_add_fts.sql
│   └── ...
├── migrate.ts          -- Migration runner
└── taskflow.db         -- SQLite database file

A `_migrations` metadata table tracks applied migrations:

```sql
CREATE TABLE IF NOT EXISTS _migrations (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL UNIQUE,
  applied_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ','now'))
);

### Migration Sequence

| # | File | Description | Destructive? |
|---|------|-------------|:------------:|
| 001 | `001_initial_schema.sql` | Create `users`, `categories`, `tasks`, `refresh_tokens` tables with all indexes, constraints, and triggers | No (creates new tables) |
| 002 | `002_add_fts.sql` | Create `tasks_fts` virtual table and sync triggers | No (additive) |

### Rollback Strategy

- **SQLite limitation:** `ALTER TABLE DROP COLUMN` is only available in SQLite 3.35+. For destructive rollbacks, the approach is: create new table → copy data → drop old → rename.
- Each migration file MAY include a `-- DOWN` section containing reverse SQL. The migration runner supports `migrate down <name>`.
- **Recommended approach for v1:** Since this is a single-user app with no production data initially, rollback = delete `taskflow.db` and re-run all migrations. After launch, rollbacks use the `-- DOWN` sections.

### Zero-Downtime Approach

Not applicable for v1 — SQLite is a single-file embedded database with one user. Migration runs at application startup before the Express server begins listening. The startup sequence is:

1. Open SQLite connection with WAL mode
2. Run pending migrations (wrapped in a transaction per migration)
3. Start Express server

## Query Patterns

### Q1: Login (AuthService)

```sql
SELECT id, email, password_hash, name FROM users WHERE email = ?;
- **Frequency:** Every login attempt
- **Plan:** Index scan on `idx_users_email` → single row
- **Expected:** < 0.1ms

### Q2: Dashboard — Today's Tasks (DashboardService)

```sql
SELECT t.id, t.title, t.priority, t.status, t.due_date, c.name AS category_name, c.color AS category_color
FROM tasks t
LEFT JOIN categories c ON t.category_id = c.id
WHERE t.user_id = ? AND t.status = 'incomplete' AND t.due_date = date('now')
ORDER BY
  CASE t.priority WHEN 'high' THEN 1 WHEN 'medium' THEN 2 WHEN 'low' THEN 3 END;
- **Frequency:** Every dashboard load (most common page)
- **Plan:** Index scan on `idx_tasks_user_id_due_date`, filter on status
- **Expected:** < 1ms for < 1000 tasks

### Q3: Dashboard — Overdue Tasks (DashboardService)

```sql
SELECT t.id, t.title, t.priority, t.due_date, c.name AS category_name, c.color AS category_color
FROM tasks t
LEFT JOIN categories c ON t.category_id = c.id
WHERE t.user_id = ? AND t.status = 'incomplete' AND t.due_date < date('now')
ORDER BY t.due_date ASC;
- **Frequency:** Every dashboard load
- **Plan:** Index scan on `idx_tasks_user_id_due_date` with range condition

### Q4: Dashboard — Completion Stats (DashboardService)

```sql
SELECT
  COUNT(*) FILTER (WHERE completed_at >= date('now'))           AS completed_today,
  COUNT(*) FILTER (WHERE completed_at >= date('now', '-6 days')) AS completed_week,
  COUNT(*) FILTER (WHERE status = 'complete')                    AS completed_total,
  COUNT(*)                                                       AS total
FROM tasks
WHERE user_id = ?;
- **Frequency:** Every dashboard load
- **Plan:** Full scan on user's tasks (acceptable — single user, < 10k rows expected)
- **Note:** SQLite 3.30+ supports `FILTER` clause. Fallback: use `SUM(CASE WHEN ... THEN 1 ELSE 0 END)`.

### Q5: Task List with Filters (TaskService)

```sql
SELECT t.*, c.name AS category_name, c.color AS category_color
FROM tasks t
LEFT JOIN categories c ON t.category_id = c.id
WHERE t.user_id = ?
  AND (? IS NULL OR t.status = ?)
  AND (? IS NULL OR t.priority = ?)
  AND (? IS NULL OR t.category_id = ?)
ORDER BY t.created_at DESC
LIMIT ? OFFSET ?;
- **Frequency:** Every task list view, filter change
- **Plan:** Uses composite indexes depending on active filters; SQLite's query planner handles `IS NULL OR` pattern well
- **Pagination:** Cursor-based pagination preferred but offset-based acceptable for v1 (single user, small dataset)

### Q6: Full-Text Search (TaskService)

```sql
SELECT t.*, c.name AS category_name, c.color AS category_color,
       bm25(tasks_fts) AS rank
FROM tasks_fts
JOIN tasks t ON t.rowid = tasks_fts.rowid
LEFT JOIN categories c ON t.category_id = c.id
WHERE tasks_fts MATCH ? AND t.user_id = ?
ORDER BY rank
LIMIT 20;
- **Frequency:** On search input (debounced 300ms per `03_frontend_lead.md`)
- **Plan:** FTS5 index scan → join on rowid → filter by user_id

### Q7: Token Refresh (AuthService)

```sql
SELECT id, user_id, expires_at, revoked_at FROM refresh_tokens
WHERE token_hash = ? AND revoked_at IS NULL AND expires_at > strftime('%Y-%m-%dT%H:%M:%fZ','now');
- **Frequency:** Every 15 minutes (access token expiry)
- **Plan:** Index scan on `idx_refresh_tokens_token_hash` → single row

### Q8: Sync — Get Changes Since Timestamp (SyncService)

```sql
SELECT * FROM tasks WHERE user_id = ? AND updated_at > ? ORDER BY updated_at ASC;
SELECT * FROM categories WHERE user_id = ? AND updated_at > ? ORDER BY updated_at ASC;
- **Frequency:** On reconnect after offline period
- **Plan:** Scans user's rows filtered by `updated_at` — acceptable for small dataset

## Data Integrity

### Foreign Keys

| Relationship | FK Column | References | ON DELETE | ON UPDATE | Rationale |
|-------------|-----------|------------|-----------|-----------|-----------|
| `refresh_tokens` → `users` | `user_id` | `users(id)` | `CASCADE` | `CASCADE` | User deletion removes all tokens |
| `categories` → `users` | `user_id` | `users(id)` | `CASCADE` | `CASCADE` | User deletion removes all categories |
| `tasks` → `users` | `user_id` | `users(id)` | `CASCADE` | `CASCADE` | User deletion removes all tasks |
| `tasks` → `categories` | `category_id` | `categories(id)` | `SET NULL` | `CASCADE` | Category deletion orphans tasks (keeps task, clears category) — per PM spec |

**Critical:** `PRAGMA foreign_keys = ON;` MUST be set on every connection. SQLite does not enable foreign key enforcement by default.

### Triggers

#### 1. Auto-update `updated_at` on tasks

```sql
CREATE TRIGGER trg_tasks_updated_at
AFTER UPDATE ON tasks
FOR EACH ROW
WHEN OLD.updated_at = NEW.updated_at
BEGIN
  UPDATE tasks SET updated_at = strftime('%Y-%m-%dT%H:%M:%fZ','now') WHERE id = NEW.id;
END;

#### 2. Auto-update `updated_at` on categories

```sql
CREATE TRIGGER trg_categories_updated_at
AFTER UPDATE ON categories
FOR EACH ROW
WHEN OLD.updated_at = NEW.updated_at
BEGIN
  UPDATE categories SET updated_at = strftime('%Y-%m-%dT%H:%M:%fZ','now') WHERE id = NEW.id;
END;

#### 3. FTS5 Sync Triggers

```sql
-- Insert
CREATE TRIGGER trg_tasks_fts_insert AFTER INSERT ON tasks BEGIN
  INSERT INTO tasks_fts(rowid, title, description) VALUES (NEW.rowid, NEW.title, NEW.description);
END;

-- Update
CREATE TRIGGER trg_tasks_fts_update AFTER UPDATE ON tasks BEGIN
  INSERT INTO tasks_fts(tasks_fts, rowid, title, description) VALUES('delete', OLD.rowid, OLD.title, OLD.description);
  INSERT INTO tasks_fts(rowid, title, description) VALUES (NEW.rowid, NEW.title, NEW.description);
END;

-- Delete
CREATE TRIGGER trg_tasks_fts_delete AFTER DELETE ON tasks BEGIN
  INSERT INTO tasks_fts(tasks_fts, rowid, title, description) VALUES('delete', OLD.rowid, OLD.title, OLD.description);
END;

## Performance Considerations

### Connection Pooling

Not applicable in the traditional sense. `better-sqlite3` uses synchronous calls on a single connection. For TaskFlow:

- **Single connection** opened at startup, reused for all requests.
- WAL mode allows concurrent reads, but writes are serialized (acceptable for single-user).
- Connection is closed gracefully on `SIGTERM`/`SIGINT`.

### Read Replicas

Not applicable — single SQLite file, single user.

### Partitioning

Not needed. Expected data volume:

| Entity | Expected Max (v1) | Growth Rate |
|--------|-------------------|-------------|
| Users | 1 | — |
| Tasks | ~5,000 | ~10/day |
| Categories | ~20 | Rarely changes |
| Refresh Tokens | ~100 (with cleanup) | 1–4/day |

SQLite handles millions of rows efficiently. No partitioning required.

### Database File Size

- Expected: < 5MB for typical usage
- FTS5 index adds ~30% overhead on indexed text
- WAL file (`taskflow.db-wal`) may grow during write bursts; checkpoint runs automatically

### Query Performance Budget

Per the SRS success criteria ("page load under 1 second"):

| Query | Budget | Expected |
|-------|--------|----------|
| Dashboard (3 queries) | < 50ms total | < 5ms |
| Task list (filtered) | < 30ms | < 3ms |
| Full-text search | < 50ms | < 10ms |
| Task CRUD | < 10ms | < 1ms |

## Backup and Recovery

### Backup Strategy

| Method | Frequency | Retention | Notes |
|--------|-----------|-----------|-------|
| **SQLite `.backup` API** | Daily (cron) | 7 daily, 4 weekly | Uses `better-sqlite3`'s `backup()` method — online backup, no downtime. Copies to `backups/taskflow-YYYY-MM-DD.db`. |
| **File copy (WAL checkpoint first)** | Before migrations | Kept until migration verified | `PRAGMA wal_checkpoint(TRUNCATE)` then `cp taskflow.db taskflow-pre-migration.db` |
| **User-initiated export** | On demand | User's device | Future feature: export tasks as JSON/CSV from the dashboard |

### Backup Script

```bash
#!/bin/bash
# db/backup.sh — called by cron daily at 02:00
BACKUP_DIR="backups"
DB_PATH="db/taskflow.db"
TIMESTAMP=$(date +%Y-%m-%d)
mkdir -p "$BACKUP_DIR"
sqlite3 "$DB_PATH" ".backup '$BACKUP_DIR/taskflow-$TIMESTAMP.db'"
# Prune backups older than 30 days
find "$BACKUP_DIR" -name "taskflow-*.db" -mtime +30 -delete

### Recovery Targets

| Metric | Target | Rationale |
|--------|--------|-----------|
| **RPO** (Recovery Point Objective) | 24 hours | Daily backups; single-user app — data loss is limited to one day of personal tasks |
| **RTO** (Recovery Time Objective) | 5 minutes | Copy backup file → rename → restart app. No complex restore procedure. |

### PWA Offline Data

The service worker (per `03_frontend_lead.md`) maintains an IndexedDB cache of tasks and categories on the client. In a catastrophic server data loss scenario:

1. User opens app (data loads from IndexedDB)
2. Sync service pushes local data to server on reconnect
3. Server database is repopulated from client cache

This provides an additional (informal) backup layer.

## Open Questions

| # | Question | Impact | Proposed Resolution |
|---|----------|--------|---------------------|
| 1 | **Should `completed_at` be set via trigger or service layer?** | Consistency vs. simplicity. A trigger guarantees `completed_at` is always in sync with `status`, but adds implicit behavior. | **Proposed: Service layer.** The TaskService already handles status transitions; setting `completed_at` there is explicit and testable. |
| 2 | **Conflict resolution strategy for offline sync?** | When the same task is modified both offline and online, which version wins? | **Proposed: Last-write-wins based on `updated_at`.** Simple, predictable. The `02_backend_lead.md` SyncService should implement this. Needs alignment with frontend lead. |
| 3 | **Should expired refresh tokens be cleaned up on a schedule or lazily?** | Unbounded growth of `refresh_tokens` table (minor concern for single user). | **Proposed: Lazy cleanup on login.** When a user logs in, delete all tokens where `expires_at < datetime('now')`. No cron needed for v1. |
| 4 | **FTS5 tokenizer locale support?** | If users enter non-ASCII task titles, search quality may vary. | **Proposed: `unicode61 remove_diacritics 2`** handles most Latin-script languages. Reassess if user feedback indicates issues. |
| 5 | **Should task `id` use UUID v4 (via npm package) or SQLite `randomblob`?** | `randomblob(16)` is not RFC 4122 compliant but is unique enough for single-user. Frontend may generate IDs offline for sync. | **Proposed: Use `crypto.randomUUID()` in the service layer** (Node 19+). This ensures RFC 4122 compliance and allows the frontend to generate IDs offline for optimistic creation. SQLite default is a fallback only. |

This is the complete `04_db_architect.md` specification for TaskFlow. Key design decisions:

1. **SQLite with WAL mode** — perfect fit for a single-user PWA with offline support
2. **4 tables + 1 FTS5 virtual table** — `users`, `refresh_tokens`, `categories`, `tasks`, `tasks_fts`
3. **All TEXT types for IDs/timestamps** — SQLite best practice; ISO 8601 for datetime comparisons
4. **11 indexes** — each justified by a specific query pattern from the dashboard, filters, auth, and sync flows
5. **5 triggers** — 2 for `updated_at` auto-management, 3 for FTS5 synchronization
6. **Explicit soft-delete decisions** — only `refresh_tokens` uses soft-delete (via `revoked_at`); all other entities use hard delete
7. **`ON DELETE SET NULL`** for tasks→categories — preserves tasks when a category is removed
8. **`PRAGMA foreign_keys = ON`** mandatory — SQLite doesn't enforce FKs by default
