# Proposal Review — Researcher A (GSD Expert)
**Date:** 2026-03-21

## Overall Assessment
**Approve with changes.** The proposal is strong — it correctly identifies AutoSpec's white space (SRS-in, role-specs-out), adopts GSD's most important patterns (zero-config auth, XML-tagged prompts, deterministic scaffolding), and proposes a sensible provider architecture. However, there are several GSD lessons that were partially absorbed or missed entirely, and a few architectural decisions that warrant reconsideration before implementation.

## What the Proposal Gets Right

1. **Provider detection priority chain mirrors GSD v1's piggybacking model.** The proposal correctly places CLI-based providers (Claude Code, Gemini, Copilot) above API-key providers, and the `isAvailable()` checks use the same logic I documented: `which claude` + auth status verification. The zero-config principle is preserved faithfully.

2. **Chained sequential pipeline over mega-prompt is the right call.** GSD's core insight is that fresh, scoped contexts produce better output than long, accumulated ones. The proposal's 13-step pipeline — one LLM call per spec with deterministic summary extraction between steps — directly applies GSD's "context rot elimination" principle without over-engineering into full multi-agent orchestration. For a generation tool (not an execution tool), this is the appropriate level of complexity.

3. **XML-tagged prompt structure adopted correctly.** The system prompt template using `<role>`, `<output_format>`, `<constraints>`, `<project_metadata>`, `<prior_spec_summaries>`, `<input_document>` is a faithful adaptation of GSD's `<objective>`, `<execution_context>`, `<process>` pattern. The tags are more specific to AutoSpec's domain, which is good — they should not be identical to GSD's, just structurally equivalent.

4. **Deterministic scaffolding principle applied well.** File names (`01_product_manager.md` through `10_ui_designer.md`), output directory structure, YAML frontmatter schema, and the summary extraction function are all handled in code, not delegated to the LLM. This directly follows GSD's strongest engineering principle.

## Concerns & Suggestions

1. **The fallback chain across providers is risky and should be opt-in, not automatic.** The proposal says that on auth errors (401, 403), the system "skips to next provider in priority chain." This is dangerous. If a user's Claude Code subscription is rate-limited and the system silently falls back to their `ANTHROPIC_API_KEY`, they may incur unexpected API charges. GSD v1 avoids this entirely by having no fallback — it uses exactly one runtime. GSD v2 has fallback models but within the same provider (e.g., Opus falls back to Sonnet, not Anthropic falls back to OpenAI). **Recommendation:** Auto-fallback should be disabled by default. If the primary provider fails, halt and tell the user. Add `--fallback` flag to opt in.

2. **The CopilotSDKProvider implementation is speculative.** The proposal's `@github/copilot-sdk` code uses `CopilotClient`, `createSession`, `assistant.message_delta`, and `session.idle` events — none of which are documented in a stable public API. The proposal itself acknowledges this in Open Question #3. **Recommendation:** Remove the Copilot SDK provider from the v0.2.0 scope entirely. Don't ship speculative code. Add it in v0.3.0 when the SDK stabilizes. This reduces the provider count from 6 to 5, which is still excellent coverage.

3. **The deterministic summary extraction function is too crude.** The `summarizeSpec()` function extracts headers, tables, and code blocks — but misses the most important cross-spec data: entity names, API endpoint paths, persona names, and technology choices. If the PM spec defines personas "Sivan" and "Maya", the backend spec needs those names, not just the section headers. **Recommendation:** Add named entity extraction (regex for capitalized names after "persona:", "user:", "role:" patterns), API path extraction (`/api/v1/...` patterns), and tech stack terms. Still deterministic, still no LLM call, but much more useful for downstream specs.

4. **The 300-line minimum validation is arbitrary and potentially counterproductive.** Some specs (marketing lead, finance lead) may legitimately be 150-200 lines for a small project. Forcing 300 lines incentivizes the LLM to pad with generic content. **Recommendation:** Make minimum line count proportional to SRS input length, or use a per-role minimum (e.g., backend/QA: 300+, marketing/finance: 150+). Better yet, validate by required sections present rather than raw line count.

5. **No `--parallel` flag for independent specs.** The proposal chose chained sequential over parallel, with good reasoning (later specs reference earlier ones). But specs 07 (marketing), 08 (finance), and 09 (business) are largely independent of the technical specs 02-06. GSD's wave-based execution pattern — run independent work in parallel, serialize dependent work — would apply here. **Recommendation:** Add a `--parallel` flag (off by default) that generates specs 07-09 in parallel after 01-06 complete. This could cut total generation time by 20-30%.

6. **Missing: `--resume` for interrupted runs.** The proposal mentions idempotency ("re-running skips completed specs") but doesn't specify the mechanism. Does it check file existence? File hash against SRS hash? Timestamp? GSD v2's crash recovery uses lock files and session files. **Recommendation:** Define the resume mechanism explicitly. Simplest: check if `specs/XX_role.md` exists AND its frontmatter `source_hash` matches the current SRS hash. If both true, skip. Otherwise, regenerate.

7. **The `.autospec-meta.json` file should be `.gitignore`-able but not by default.** Cost data and timestamps are useful for teams but noise for OSS repos. **Recommendation:** Mention in docs that users can gitignore it, but don't auto-add it to `.gitignore`.

8. **Missing error UX for subprocess providers.** What happens when `claude -p` is available but the user's Claude Max subscription has hit its daily limit? The subprocess returns a non-zero exit code with an error message to stderr, but the proposal doesn't show how that error is parsed or presented. **Recommendation:** Add stderr capture and a provider-specific error message parser. At minimum, surface the raw stderr to the user with context ("Claude Code reported: ...").

## GSD-Specific Gaps

1. **GSD's "prompt-framework-first" lesson was only half-learned.** My research report's Key Lesson #1 emphasized that GSD v1's most elegant decision is that it is *not a runtime* — it installs instructions into existing runtimes. The proposal correctly adopts the auth-piggybacking aspect, but misses the deeper implication: AutoSpec could also ship `.claude/commands/autospec/` slash commands that let users run `autospec generate` from *within* Claude Code as `/autospec:generate`, not just from the terminal. GSD does both (commands inside runtimes + CLI invocation in v2). The proposal's Open Question #7 touches this ("Skills integration path") but treats it as separate. **Recommendation:** At minimum, document this as a v0.3.0 goal. The slash-command distribution path would give AutoSpec reach into the same 23k+ user base that GSD targets.

2. **GSD's state file schema is human-writable by design — the proposal's `.autospec-meta.json` is not.** GSD deliberately uses Markdown for all state because users can read and edit it. The proposal uses JSON for metadata. This is fine for machine-readable metadata, but the proposal should ensure that the *generated specs themselves* remain the canonical state — not the JSON file. If the JSON file is deleted, `autospec` should still work by reading the specs directory. **Recommendation:** Make `.autospec-meta.json` purely informational, never required for operation.

3. **GSD's `@./` file reference pattern for lazy loading was not adopted.** In GSD v1, prompts reference files with `@./PROJECT.md` syntax, and the runtime loads them at dispatch time — not when the prompt is authored. The proposal inlines all content eagerly (SRS content injected via Handlebars template at compile time). For small SRS documents this is fine, but for large ones (10k+ words), the `<input_document>` section could dominate the context. **Recommendation:** For SRS documents over a configurable threshold (e.g., 5,000 words), add a chunking/summarization step before injection, or truncate to the most relevant sections per role. The backend lead doesn't need the full marketing requirements section of the SRS, and vice versa.

4. **GSD's verification phase has no equivalent.** GSD's pipeline is discuss-plan-execute-**verify**. The proposal has a validation step (step 12), but it only checks structural properties (frontmatter, line count, section headers). It does not verify *content quality* — e.g., does the backend spec actually define endpoints for every user story in the PM spec? Does the QA spec reference every API endpoint from the backend spec? **Recommendation:** Add an optional `--verify` flag that runs a lightweight LLM call to cross-check spec coherence. Not required for v0.2.0, but design the pipeline to accommodate it.

5. **GSD's tiered model selection is acknowledged but not implemented.** My research documented GSD v2's model routing (Opus for planning, Sonnet for execution). The proposal's Open Question #1 asks about this but doesn't propose a default. **Recommendation:** Ship with a simple default: use the provider's default model for all specs, but accept `--model` override. Add per-role model routing in a future version. Don't over-engineer this before cost data exists.

## Verdict

The proposal is architecturally sound, well-differentiated from competitors, and correctly applies the most important GSD lessons. The five concerns above are all addressable without major redesign. The most critical change is #1 (make cross-provider fallback opt-in) — silent cost escalation would damage user trust. The most valuable addition would be GSD Gap #1 (ship slash commands for AI runtimes alongside the standalone CLI) — this expands the addressable user base significantly.

**Recommendation: Approve with the five changes noted above, defer Copilot SDK to v0.3.0, and add slash-command distribution to the v0.3.0 roadmap.**
